# 双电脑同步与改进

安装到 AGENTS 的内容是生成副本；共同规则以你选择的 Git 仓库为源。公开上游只接收通用且脱敏的改进。个人信息、工作细节或不适合公开的偏好，保存在独立私有派生仓库或本机文件；不要试图把公共仓库的分支当作私密空间。脚本不配置自动同步或跨机运行。

## 首次连接远端

执行对话在既有认证与明确仓库授权范围内建立/连接规则源的独立仓库；是否公开按内容和用户授权决定。不要在整个工作根目录 git init，不上传 `.assistant-workflow/`、`.local/`、认证、聊天或项目资料。另一台 clone 后只需读取 START_HERE.md 接入。

## 在任一电脑改进

1. 新用户要求由执行者判断：共同规则、本机设置、项目决定，还是未确认建议。
2. 已确认共同规则改 rules/COMMON.md，递增 VERSION，在 CHANGELOG.md 记日期、确认来源摘要、行为变化与适用范围。来源用概括性说明；公开版本不记录真实线程、客户、家庭、雇主或项目细节，具体证据只留本机或私有记录。不要把 agent 的建议直接写成用户规则。
3. 先同步远端变化，合并后预览并更新本机 AGENTS；通过必要检查后，在已有同步授权范围内提交推送。每次公开推送前再次检查文件、差异和新增 Git 历史，去掉真实用户记录、设备路径、线程、账号、业务数据与认证；不能直接把实际 AGENTS 或本机记录上传。不因常规同步反复请用户确认。
4. 未确认的改进在讨论后采用；本机路径/能力/账户/权限和日程实例只留本机，不进共同源。

## 另一台如何得到更新

开始或恢复协作时，由执行对话检查规则包版本与 Git 状态；不要让主对话自己跑命令。无本地未提交改动时可用 `git pull --ff-only`；有本地改动时先保留并合并，不 reset --hard、不无提示 stash。远端不可用时继续已安装版本并标记未同步。

随后运行 install 预览和应用，再用 status 看文件状态。规则是在会话启动时建立指令链；新会话/重开的实际加载仍须核实。规则更新不是运行中会话热更新承诺。

没有配置任何自动拉取服务。若用户希望无人介入同步，可由选定的唯一调度者在既有日程中派发一次同步检查；另行配置并验证之前不宣称自动同步已开启，不擅自给两台各加一个日程。

## 两边同时改了怎么办

Git 无冲突快进时直接更新；不同部分可由执行者合并。相同规则有行为冲突时，展示两边改动与各自确认来源，集中向用户确认取舍，合并后再发布一个新版本。私有设备资料放 local.md，相关任务按需读取；需要常驻加载的项目规则保留在该项目原入口，并核对其公开范围。不要把私密笔记当作可提交指令片段。

安装区块若被手改，install 会停止并显示已安装基线与当前区块的差异。执行者先把用户确认的通用改动合回 COMMON.md，把私有机器资料放 local.md，把适合常驻的项目规则留在项目原入口，再恢复受管理基线后正常更新；不得不看差异就覆盖。

## 没有远端时

可复制整个规则包到另一台，照 START_HERE.md 接入。每次复制前比较 VERSION 与 COMMON.md 校验和，保留接收端改动；这只是人工文件交换，不是自动双向同步。远端 Git 用于保留版本、来源和冲突记录，不承诺它会同步 App 权限、会话或后台任务。

## 一个调度者

两台可以各自有主对话，但同一项目/日程需明确一台负责；接管不是复制 automation ID。项目 plans 应记录负责设备与任务范围。另一台默认不创建重复任务或循环，转交时先交接旧任务与实际状态。不要把 Git 规则同步当成任务队列。
